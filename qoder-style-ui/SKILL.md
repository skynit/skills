# Qoder 视觉风格

这是一个 **UI 风格 skill**，不是功能设计 skill。它回答“界面应该长什么样”，不回答“页面应该有哪些功能、入口、路由、数据或流程”。

先把目标项目已有的功能、内容、信息架构和交互保持不变，再把视觉表现替换为 Qoder 式桌面工具质感。只有用户明确要求功能改造时，才能调整结构或行为。

## 风格与功能边界

- **视觉风格**：颜色、字体、字号、间距、边框、圆角、阴影、图标、密度、控件外形、状态外观和主题切换方式。
- **信息架构**：页面分成几组、导航有哪些入口、设置项如何分类。
- **交互流程**：点击后做什么、权限如何申请、数据如何提交、任务如何流转。
- **业务能力**：有哪些真实功能、接口、模型、账户、连接或资源。

本 skill 只控制第一项。后三项由目标产品和用户决定。

除非明确授权，不要：

- 增删页面、导航、设置项、字段、按钮或业务动作。
- 为了“更像 Qoder”重写功能逻辑、数据模型、接口或路由。
- 编造示例数据、账户信息、统计数字、连接状态或能力。
- 复制 Qoder 的商标、Logo、专有图标、文案、截图或个人资料。

设置页、账户页、对话工作区、表格、表单、编辑器、代码审查等都可以使用这套视觉语言，但它们只是示例，不是 skill 的限定范围。

## 术语

- **Qoder**：一款 AI IDE 与桌面工作工具。本 skill 只借用其可观察的视觉语言，不声称能访问其私有代码、设计系统或品牌资产。
- **设计令牌（Design Tokens）**：用语义名称保存的 CSS 变量，例如背景、表面、边框、文字、强调色和危险色。组件引用令牌，而不是到处写十六进制颜色。
- **Electron**：用 Chromium 承载 Web 界面的桌面外壳。它解释桌面端为什么可以像网页，但不决定视觉风格。
- **React**：组件化 UI 库。它属于实现技术，不等于 Qoder 风格；Vue、Svelte 或其他框架也能实现同一视觉语言。
- **`data-theme` 与 `data-style`**：分别选择颜色主题和密度/形状风格的两个根元素属性。两者独立，例如暗色主题可以配紧凑风格。
- **AppShell**：产品原有的持久外壳，如标题栏、侧栏和主工作区。这里只改变其视觉表现，不重新定义应用结构。
- **视觉回归**：只比较同一功能和内容在改造前后的外观，确认布局稳定、可读性和可访问性没有下降。

## 何时使用

适用于：

- “把这个界面做成 Qoder 风格。”
- “参考截图改颜色、字体、间距、控件和整体质感。”
- “给现有设置页、对话页、编辑器或任何桌面工具换成 Qoder 式视觉语言。”
- “建立一套接近 Qoder 的明暗主题和组件样式。”

不适用于：

- 设计产品应该有哪些功能、页面、字段、流程或权限。
- 单纯实现后端、数据结构或业务逻辑。
- 未经授权地制作包含 Qoder 商标、素材或真实用户信息的仿冒界面。

## 执行顺序

1. **先读目标项目约束。** 检查 `AGENTS.md`、现有设计系统、组件库、主题变量、图标库和对应 package 的检查命令。已有视觉规范与用户要求冲突时，以当前项目规范和用户明确选择为准。
2. **盘点现有界面。** 记录目标页面当前的信息层级、主要控件、固定尺寸区域、滚动区、响应式断点和状态。不要把“视觉改造”扩大成功能重排。
3. **选择视觉改造层。** 优先替换设计令牌，再统一基础控件，最后处理局部布局质感。不要从单页硬编码开始，否则后续会出现多套近似颜色和边框。
4. **建立主题。** 先完成 `light` 与 `dark` 的语义色，再按需要增加独立的 `data-style` 密度/形状变体。默认 `neutral`。
5. **遵守预览门禁。** 目标仓库或用户要求 Preview-first 时，在写页面 Vue/CSS/React 前生成 `1440x900` 预览，必要时补 `960x640`；展示并获准后再实现。
6. **实施视觉层。** 保留原有 DOM 语义、交互、数据和路由。若必须调整标记以支持样式，保持可访问名称、键盘顺序和原有行为不变。
7. **按影响面验证。** 只运行受影响 package 的类型检查、该 package 的组件测试和视觉检查。禁止全仓测试或无关构建。
8. **检查视觉回归。** 对比改造前后的关键界面，检查溢出、遮挡、焦点环、长文本、明暗主题和目标窄视口。

## 视觉特征

这套风格的识别点不是某个页面，而是以下可复用规则：

- 暖中性浅色面或低眩光深灰面，不使用强烈蓝黑或紫色调。
- 低饱和边框和选中面优先于阴影；只在浮层使用少量阴影。
- 蓝色只承担交互强调，绿色、琥珀色和红色只承担真实语义。
- 字体紧凑、克制，正文 13–14px；不使用负字距和随 viewport 缩放的字体。
- 控件高度常见 30–40px，圆角常见 4–10px，间距从 4/8/12/16/24/32px 中选取。
- 细线图标、低对比分隔线、稳定控件列和小面积状态标签。
- 点阵纹理只用于非常有限的背景区域，不覆盖正文和控件。
- 外观平静，但通过密度、边框和层级保持可扫描性。

## 不可偏离的规则

- 不改变产品功能、信息架构或业务流程来迎合风格。
- 不使用大面积玻璃拟态、渐变球、bokeh、装饰光晕或营销式 hero。
- 不让颜色成为唯一状态通道；必须保留文字、图标或 accessible name。
- 浅色和暗色主题都要检查对比度、焦点和危险语义。
- 文本不能只靠 viewport 字号缩放；长内容必须有换行、ellipsis 或详情入口。
- 图标使用 lucide 或项目现有图标库，不混用 emoji、手绘 SVG 和多套风格。
- 不把 Qoder 截图中的个人资料、工作区内容或业务数据复制到其他项目。

## 资源路由

- 确定视觉方向、颜色、字体和密度时，读 [视觉语言](references/visual-language.md)。
- 定义基础控件、状态和组件外观时，读 [控件视觉规范](references/component-styling.md)。
- 写 React/Vue/CSS、处理主题、可访问性和视觉验收时，读 [实施与验收](references/implementation.md)。
- 需要快速启动时，复制并按项目命名改造 [qoder-ui.css](assets/qoder-ui.css)。它提供视觉原语和示例类，不代表产品必须采用这些页面结构。

不要把 `@design-llm/qoder-design` 当作必然可用的公共依赖。只有目标项目已经安装并在 lockfile 中确认它存在时才能导入；否则按本 skill 的令牌和控件规则自建，不臆造包 API。

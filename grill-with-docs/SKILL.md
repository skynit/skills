# 设计访谈与文档

通过有依赖顺序的问题澄清方案，同时让术语、真实代码和已确认决定保持一致。本入口自包含访谈与领域定义流程，无需另行加载同类技能。

## 确定范围

1. 读取用户目标、相关实现和适用 `AGENTS.md`，复用既有方案、定义与决策。已有 `GLOSSARY-MAP.md` 时按映射定位词汇表；没有专门词汇表也不阻塞讨论。
2. 明确本轮是推敲设计、核对术语还是两者同时进行。只核对一个定义时可直接查证与解释，已有明确答案的问题不重复访谈。
3. 分清源码事实和用户决策。事实由 Agent 查证，取舍才向用户提问；工具或环境不足时说明具体缺口，不把猜测记成结论。
4. 按当前授权处理文档：只读讨论给出拟议条目，文档修改仅写入指定范围。访谈不自动授权源码改动、创建任务单、对外发布或另建文档体系。

## 分轮追问设计

- 将决定按前置依赖组织。每轮只问前提已确定的问题；同轮问题不依赖尚未获得的答案。
- 每个问题说明需要决定什么、推荐答案和关键影响，便于用户接受推荐或指出差异。优先处理会改变方案方向或实现边界的决定，控制单轮认知负担。
- 每轮回答后整理已确认结论，更新后续问题；已有指令已解决的事项不反复索取确认。
- 结合具体场景核查正常、失败、取消、并发或兼容分支，只检查当前方案实际涉及的边界。对代码能回答的部分先读取调用链。
- 关键分支都已检查、没有影响本轮目标的隐含假设时结束；缺信息的事项单独列为未决，不宣称已经达成一致。

问题可以采用以下形式：

```text
Q1：需要决定的行为及其前提。
推荐：具体选择。
影响：它会改变哪些用户行为、职责或验证条件。
```

## 同步领域定义与决策

- 用户用词与已有定义冲突时，指出具体差异并核实本轮实际含义。概念含糊或重载时，给出准确名称并用场景区分；保持项目已有的准确术语。
- 说明业务概念是什么、由谁创建或配置、承担什么职责及与相近概念的关系，再对照代码。用户描述与实现不符时明确指出，不静默改变任意一方。
- 词汇表记录项目业务含义，不存实施细节、临时假设或整个规格。没有既有格式且确需新建时，读取[词汇表格式](references/GLOSSARY-FORMAT.md)；新文件仍须位于当前文档授权范围。
- ADR 是记录重要架构取舍及原因的文档。只有决定难逆转、缺背景会令人意外、确有备选方案取舍三项同时满足时才建议记录；需要新格式时读取[决策记录格式](references/ADR-FORMAT.md)。
- 优先更新现有定义和相关条目；协作约束由所属 `AGENTS.md` 统一维护。缺少文档不是另建重复规则的理由，也不强制每次讨论创建 ADR。

## 输出与完成标准

1. 总结已确定的目标、边界、取舍及依据；未决问题单列，标明由谁决定或缺什么事实。
2. 给出需要保留的领域定义和必要决策。已经授权并实际更新的文档列出路径；只读讨论展示拟议条目，区分它们与已写入内容。
3. 说明本轮实际检查的实现与约束，以及未核实的条件。若用户只要求讨论，到此结束；已有明确后续授权时在对应范围内继续，无需因换阶段重复请求同一授权。

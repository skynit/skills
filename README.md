# Codex 本地技能使用指南

这份 README 帮助你按任务选择技能，并知道应该提供什么、能够得到什么，以及何时需要换一个入口。它是使用指南；具体操作步骤、脚本参数、服务器默认配置和支持条件以每项链接的 `SKILL.md` 为准。

按 **2026-11-03** 本地文件清点，本指南收录 **82 个不重复入口**，覆盖当前技能目录、`.system/` 与共享目录 `~/.agents/skills/`。同一技能的符号链接只计一次。插件管理的文档、表格、演示文稿等入口不在本目录重复列出；本地存在也不代表当前会话已经提供，实际调用以会话可用列表为准。

## 怎么使用这份指南

1. 先看[常见任务选择](#常见任务选择)，或直接进入下面的分类。
2. 在目标条目中核对作用、使用场景与输入、预期结果与边界，再复制并补充调用示例。
3. 只有需要实际执行时再读对应技能定义；无需把全部技能和引用一次加载。
4. 一个任务跨越几个阶段时，参考最后的[工作流建议](#工作流建议)，跳过已经完成或不需要的阶段。

示例都是发给 Codex 的对话提示词，不是终端命令：

```text
$review-code-simplification 审查当前未提交改动，只给有证据的精简建议。
$review-code-simplification 精简指定文件的重复实现，保持行为不变，完成相关定向验证。
```

“显式调用”表示本地配置要求点名技能；“按任务选择，也可点名”表示配置允许根据任务选择。调用时使用 `$` 后面的**调用标识**，显示名称只是便于辨认。若当前会话没有提供本地某项入口，应先明确能力和加载情况，不声称已执行。

点名技能不能扩大当前授权。示例中的“实现、修复、部署、发布”描述会触发相应实际工作；只想了解或审查时，明确说明只读或仅输出草案。项目规定的测试范围、文档归属与已有改动保护继续适用，技能正文中的通用示例也不能覆盖这些约定。

## 常见任务选择

| 当前问题 | 先看哪个入口 | 判断依据 |
| --- | --- | --- |
| 有想法，但方向和范围没定 | [idea-refine](#idea-refine) 或 [grill-with-docs](#grill-with-docs) | 前者比较方向；后者分轮追问方案、核对术语，并按文档授权整理决定。 |

| 已明确行为，准备实现 | 直接说明修改范围；先测试时用 [tdd](#tdd) | 按项目约定实施可验证的小步，保留已有改动并做相关定向验证。 |

| 调整模块职责与封装 | [codebase-design](#codebase-design) 或 [improve-codebase-architecture](#improve-codebase-architecture) | 前者分析一个设计，后者寻找和比较一批候选。 |
| 设计视觉、实现组件或查资料 | [impeccable](#impeccable)、[frontend-ui-engineering](#frontend-ui-engineering)、[ui-ux-pro-max](#ui-ux-pro-max) | 先区分设计决策、工程实现与参考查询。 |

| 需要复盘或继续到新会话 | [retro](#retro)、[handoff](#handoff) | 前者改进后续工作方式，后者交接当前状态。 |

### idea-refine

| 项目 | 详细说明 |
| --- | --- |
| 调用方式 | **按任务选择，也可点名**；[技能定义](idea-refine/SKILL.md) |
| 作用 | 把已有但模糊的想法展开成几种可比较的方向，再依据目标、约束和风险收敛。重点是判断什么值得做、最小可行范围是什么，以及哪些假设还需要验证。 |
| 使用场景与输入 | 适合“想改善体验，但不知道做成哪种方案”。提供用户问题、现有产品、硬约束和已有想法；如果方向已选定，应转入规格或计划。 |
| 预期结果与边界 | 得到问题定义、推荐方向、关键假设、最小范围和不做事项。需要写入想法文档时按对应文档授权执行，不直接开始实现。 |
| 调用示例 | `$idea-refine 帮我比较三种 CW 分享链接管理方案，先收敛目标和最小范围，只在对话中整理结论。` |

## 实现、调试与质量

### tdd

| 项目 | 详细说明 |
| --- | --- |
| 显示名称 | TDD |
| 调用方式 | **按任务选择，也可点名**；[技能定义](tdd/SKILL.md) |
| 作用 | 通过外部可观察行为建立测试驱动循环：先让一个有效用例失败，再写足够的最小实现使其通过。测试期望来自契约或独立示例，不能照抄实现计算。 |
| 使用场景与输入 | 适合行为已明确的新功能和回归修复。提供行为与测试入口，优先复用已有边界和测试文件；接口本身未定时先讨论测试边界。 |
| 预期结果与边界 | 得到逐项验证的实现与行为测试。本地版本强调一次一个循环，结构整理放到后续审查；CW 只运行相关包和实际命中的用例。 |
| 调用示例 | `$tdd 实现分享过期后拒绝访问，先在已有测试文件补一个失败用例，再做最小修复与定向验证。` |


### diagnosing-bugs

| 项目 | 详细说明 |
| --- | --- |
| 显示名称 | Diagnosing Bugs |
| 调用方式 | **按任务选择，也可点名**；[技能定义](diagnosing-bugs/SKILL.md) |
| 作用 | 首先建立能够捕获用户具体症状的复现命令，再缩小场景、列出可验证假设、逐项排除并确认根因。性能问题先建立测量基线；偶发问题先提高复现稳定性。 |
| 使用场景与输入 | 适合报错、错误结果、资源泄漏、偶发失败和性能回退。提供症状、触发条件、日志与可访问环境；复现困难时明确说明缺少的证据。 |
| 预期结果与边界 | 得到实际执行过的复现方式、原因证据，以及已授权时的修复和回归验证。只读诊断不自动授权加日志或改源码，临时产物优先放系统临时目录。 |
| 调用示例 | `$diagnosing-bugs 诊断任务取消后后台仍运行的问题，先建立捕获该症状的复现命令；本轮只诊断。` |

## 工作流建议

工作流按任务状态选择，不要求把本目录全部技能串起来。先看当前缺的是需求、事实、实现、验证还是交付；已有可靠结果的阶段可以跳过，同一目标已有明确授权也无需因换技能再次确认。

### 1. 需求尚不清楚的新功能

1. **先澄清要做什么。** 需要比较不同方向时选 `idea-refine`；方案、边界或概念尚未明确时用 `grill-with-docs`，分轮追问并核对已有定义。目标清楚的小改动可跳过访谈。
2. **整理必要契约。** 直接要求总结目标、范围、接口、失败分支和验收条件；任务较大时按可独立验证的行为列出步骤和真实依赖。重要实施方案可用 `review-code-plan` 核实源码假设，无需额外的规格或任务发布入口。
3. **按授权实施。** 有明确源码修改授权时直接实现本轮行为；要求先测试时配合 `tdd`。在 CW 中按问题读取 `go-guide` 专题与相关包指南，保留已有工作，不自动提交。
4. **审查并验证。** `code-review-and-quality` 检查实现；有具体精简目标时使用 `review-code-simplification`。依项目约定核实实际验证结果与未覆盖条件，明确要求上线时才进入对应部署技能。

```text
$grill-with-docs 推敲 CW 分享审批方案，先查现有行为与定义，分轮确认需要我决定的取舍。
本轮只讨论，最后整理已确定需求、文档草稿与未决事项，不修改文件。
```

完成条件是需求与验收已明确，且本轮授权实现的行为有实际证据；不是整理了方案就宣称功能已完成。

### 2. 已有功能报错、偶发失败或变慢

1. **先拿到可检验事实。** 用 `diagnosing-bugs` 建立能捕获具体症状的复现命令。性能问题先固定负载并测量；桌面核心转储或内存不足则分别从 `diagnose-crash`、`diagnose-oom` 进入。
2. **核实原因后修复。** 只读诊断止于证据和建议；已有修复授权时，利用最小复现场景建立合适的回归用例，再实施最小修复。诊断流程已经包含先失败后修复时，不必为形式完整再重复一遍 TDD。
3. **复验原始问题。** 运行原始场景和相关定向测试，再由 `code-review-and-quality` 检查根因与修复是否对应。无法复现、缺硬件或只能用替身时，明确验证限制。

```text
$diagnosing-bugs 诊断任务取消后后台仍占用资源的问题，先建立实际可运行的复现命令。
定位根因后按本次修复授权修改，补合适的回归用例并复验原始场景。
```

完成条件是原始症状有可重复的验证，修复针对已确认原因，临时探针已清理。复现命令只是“不崩溃”或测试零用例执行都不够。

### 3. 精简当前改动或调整模块结构

1. **局部冗余先用统一精简入口。** `review-code-simplification` 默认检查重复、声明和可读性；只要建议时保持只读，明确要求实施时按授权执行。文件迁移和测试归并仅在有对应目标或具体候选时追加。
2. **职责问题再用架构分析。** 一个接口或封装难判断时用 `codebase-design`；某个领域反复牵动多处时用 `improve-codebase-architecture` 找候选。术语冲突使用 `grill-with-docs` 中的定义核对流程，无需把整个代码库重新命名。
3. **选定方案后再重构。** 明确范围和行为契约，必要时经 `review-code-plan` 检查，然后实施最小改动、做定向验证。保留平台边界、资源所有权和仍有价值的测试。

```text
$review-code-simplification 审查当前未提交改动，只给有证据的最小建议。
不要因实现只有一个就删除接口，文件布局只检查已经形成具体候选的部分。
```

完成条件是维护成本实际下降且相关行为有保持依据。代码行数、文件数或跳转层数的减少本身不能证明改动值得采用。

### 4. 界面设计与组件实现

| 当前缺什么 | 起点 | 下一步 |
| --- | --- | --- |
| 视觉方向、信息层级或 UX 判断 | `impeccable` | 方向明确后交给 `frontend-ui-engineering` 实现。 |
| 对同一 UI 想比较不同表达 | `prototype` | 先查看原型并选定方向，再提升为正式组件。 |
| 已有设计，需要组件、状态和交互 | `frontend-ui-engineering` | 完成后在真实浏览器核对加载、错误、空态、键盘和响应式行为。 |
| 缺某项配色、字体或图表参考 | `ui-ux-pro-max` | 只查询相关维度，结合产品选择，再回到设计或实现。 |
| 需要前端依赖选型 | `pick-ui-library` | 先检查已有依赖，决定采用后再按授权安装。 |
| 真实数据可能撑坏界面 | `break-ui` | 先观察极端数据问题，明确要修哪些再实施。 |
| 手机浏览器特有的触摸与视口问题 | `mobile-native` | 在可用的目标手机检查，记录未具备的真机条件。 |

有 Chrome DevTools MCP 时，可用 `browser-testing-with-devtools` 验证运行行为；Android、Flutter、Compose 等选择各自的平台工具与专项技能。展示图不能替代真实界面，截图也不能代替交互验收。

```text
$frontend-ui-engineering 按现有设计实现分享弹窗，覆盖加载、失败、空态和键盘焦点。
保留视觉方向，完成与本次修改直接相关的浏览器检查。
```

### 5. 动效设计、实现与审查

1. **先判断任务类型。** 不知道哪里需要动效，用 `find-animation-opportunities`；一个具体交互的手感判断，用 `emil-design-eng`。高频操作也可能应该保持即时响应。
2. **按平台实现。** Web 用 `animate`，React Native / Expo 用 `animate-expo`，Android Compose 用 `animate-compose`。用 `apple-design` 讨论直接操控、速度交接或弹簧时，仍保持目标平台与既有产品行为。
3. **按范围审查。** 单个 Web 动效或差异用 `review-animations`，Android 用 `review-android-motion`；跨多个页面的治理规划才用 `improve-animations` 或 `improve-android-motion`。审计给出计划后，另按授权实施。

```text
$animate 为现有抽屉实现可打断的打开与退出，沿用项目动效约定。
完成后检查减少动态效果、中途反向操作和键盘焦点，报告实际观察条件。
```

完成条件是目标交互、连续操作、退出和禁用动画分支都有依据。只看一次打开效果，不能证明动效在真实使用中可靠。

### 6. 构建、部署与版本交付

先选产品和产物，再选技能。下面这些入口不应互相代用：

| 要交付的对象 | 入口 | 验证重点 |
| --- | --- | --- |
| 真实 CWNAS Linux 设备上的后端改动 | `accept-code` | 目标架构、已有功能配置、实际服务与本次 API 行为。 |
| CWNAS 扫码 Android 安装包 | `build-cwnas-apk` | 移动端入口、目标平台域名、包内资源与架构。 |
| 官方穿透平台的已打包前端 | `deploy-cwnas-web` | 包来源、前端备份切换及线上页面和资源。 |
| 穿透测试平台前后端 | `deploy-tunnel-platform` | 连接、必要构建、前后端切换与基础上线结果。 |
| 知识库 Vue 前端 | `deploy-kb-frontend` | dist 产物、静态站点目录和线上资源。 |
| 官网模型 NAS 后端 | `deploy-webai-backend` | 最终主机、模型配置及本次导入、检索或对话链路。 |
| 只换限定应用文件的已有 ISO | `iso-refresh` | 已验证基线和允许替换的载荷范围。 |
| 系统、内核或安装器输入变化的 ISO | `iso-recreate` | 真实构建输入、目标变体和重建产物。 |
| 其他指定项目或驱动 | 对应项目专属入口 | 依其包内条件检查，不能套用 CWNAS 服务路径。 |

仅打包时交付产物；明确要求部署时完成目标核对、备份、切换和相应验收。重要上线还缺回滚或观察方案时可配合 `shipping-and-launch`；常规已有流程不必重复建立发布清单。构建通过、产物校验、进程存活、API 实测、客户端验收是不同层次的证据。

```text
$deploy-cwnas-web 将指定发布包部署到官方穿透平台前端，核对包来源并备份。
完成线上页面与关键资源检查，报告恢复位置和未验证内容。
```

若需要提交或 PR，按已有授权使用 `git-workflow-and-versioning` 或 `submit-upstream-pr`。发布某个项目不自动授权顺带发布其他服务。

### 7. 在 Codex 内推进实现与审查

- 已有明确方案和源码修改授权时，在当前 Codex 会话实施，按任务需要使用计划审查、TDD 和代码审查入口。
- 需要独立审查且当前 Codex 环境具备相应能力时，给审查者明确的差异、契约和验证证据；审查结果由主任务核实后处理。
- 不需要额外分工的小改动可以直接实现与定向验证；不用为走流程再启动其他类型的 Agent 或外部模型 CLI。

分工不会扩大修改、提交或发布授权。完成条件是可审阅的改动与真实验证，不能把另一个审查者的肯定当作执行证据。

### 8. 返工、知识沉淀与会话交接

| 目标 | 使用方式 | 应保留的结果 |
| --- | --- | --- |
| 避免同类返工再次发生 | `retro` 检查本次事实；需要改规则时配合 `writing-for-agents`。 | 改进候选、依据、维护位置；只在授权范围内写长期规则。 |
| Agent 经常找错资料或忽略约束 | `retro` 查明具体原因，`writing-for-agents` 审查入口和读取条件。 | 最小导航或上下文调整，而非继续堆叠重复规则。 |
| 将已确认知识融入个人笔记 | `capture-conversations-to-vault` 查重并更新。 | 有来源的可复用知识，区分未证实猜测与结论。 |
| 更换会话或交给另一个 Agent | `handoff` 生成临时交接文档。 | 目标、授权、状态、证据、未决项和下一步，引用已有产物。 |

```text
$handoff 整理本次任务交接文档，下一会话继续未完成的失败恢复验证。
列明已有授权、实际改动、已执行检查和未决问题，引用现有计划，保存到系统临时目录。
```

任务已经完成且没有可复用的新经验时，可以直接交付，不必额外生成复盘、笔记或交接文件。

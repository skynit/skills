# 扩展与异常检查

仅检查当前包实际涉及的行；这是用于发现具体耦合的工具，不要求每个包实现全部机制。

## 用第二种实现检查公共链路

选择与首个实现有实质差异的最小测试实现。例如首个实现使用密码、第二个使用令牌；首个依赖共享服务器凭据、第二个允许每资源独立凭据。通过公开服务契约走流程，而非只调用接口方法后断言返回值。

| 边界 | 检查问题 | 有效证据 |
| --- | --- | --- |
| 注册与装配 | 实现能在独立包定义吗？配置定义和执行实现是否共享同一注册集合？ | 独立测试实现可装配；重复注册明确拒绝；需要的装配顺序有说明 |
| 创建 | 公共服务是否仍要求首个协议的配置字段？ | 第二种配置可创建，缺参数与错误变体在边界被拒绝 |
| 修改 | 只改名称是否仍断言首个配置？不同认证方式能否保留或替换凭据？ | 元数据和配置分别修改；失败后重读状态无半更新 |
| 列表与详情 | 混合实现是否 panic 或输出错误协议字段？是否泄漏秘密？ | 同一列表含两种实现，公开字段各自正确 |
| 持久化 | 重开后是否还原为正确类型？是否必须改通用存储才能接入第二种实现？ | 真实主库重开与配置往返，未知配置明确失败 |
| 幂等 | 默认值展开是否稳定？修改后重放是否覆盖新配置？ | 重放复用原资源；不同参数冲突；不打印摘要中的凭据 |
| 资源约束 | 规则是否来自实现？是否按协议/端口等身份正确区分？ | 独占冲突、允许共存和不同凭据范围都有实际状态验证 |
| 缺席实现 | 数据仍可读但执行实现没加载时会怎样？ | 查看安全、动作明确失败、原记录不变、后台不崩溃 |
| 自动处理 | 是否把本地路径、UNC、平台名当成恢复能力？ | 明确支持的实现推进，不支持或证据未知的实现不被强制处理 |
| 退出 | Close 是否绕过正常路径的能力和安全检查？ | 显式关闭后再检查资源、记录、额度和动作次数 |

## 生命周期与外部效果

请求超时、子进程退出、客户端取消，只能证明该等待或执行路径结束，不能自动证明外部系统没有副作用。对需要归属证据的资源：先保存操作意图，按实际系统证据确认；证据未知时禁止擅自接管或删除。前端是否看见恢复入口由业务契约决定，隐藏入口不等于可以省掉后端安全检查。

后台循环和进程必须有启动/停止所有者；退出会等待哪些资源、哪些 IO 无法硬取消，写进对应契约。使用有界重试，不在取消后启动无主 goroutine；正常与退出清理共享同一能力约束。测试在资源释放前后、服务关闭后分别检查状态，不能只在 deferred Close 之前检查。

## 凭据与配置

配置对象不包含待持久化的明文秘密，公开详情使用字段集合而非直接序列化内部记录。长令牌、多字段凭据和证书若确属需求，确认加密存储、传输限额和辅助进程输入都容纳它们；不要把未验证的凭据形式宣称为已支持。

复用项目的认证加密方案；完整验证创建、更新、重开后的解密和公开脱敏。安全用例应包含长度边界、错误版本、截断/篡改、跨资源用途复用以及失败时不调用外部执行器。不打印或提交真实凭据。更换已有密文格式时按当前项目兼容策略处理，并明确影响。

## 分层和可变配置

- 消费者端口表达业务所需行为；具体系统命令、网络 SDK、平台属性与持久化语句留在适配层。
- JSON 字节在 HTTP、文件或进程边界转为强类型；公共领域用例不重复解析字段。注册表依赖若影响解码，应显式装配；不要把整个进程的初始化顺序隐藏在实体构造里。
- 配置修改返回独立的新值；指针或 map 实现不应先改掉共享旧对象，再在验证失败时声称没有变化。
- 能力接口可选时，缺失意味着明示的不支持；同一个接口在后台、手动操作和退出阶段含义要一致。
- 如果项目只允许有限的业务变体，显式类型分支可能比插件注册更简单。只有用户需要独立新增实现时才扩张开放注册契约，并据此验证跨包实现能力。

## 不把旧案例变成通用规定

有数据库才需要事务端口，有外部效果才需要归属/恢复设计，有多协议才需要协议配置分派。小型纯计算包无需 routes/storage/infra/注册表，短同步操作无需引入任务管理。以当前需求和项目已有模式决定最小结构。

# 构建 Go 领域包

让新包在当前项目中职责明确、依赖方向正确、扩展能力有实际证据。默认建立满足需求的最小结构，不为形式上的分层批量创建目录、接口或空实现。

## 先确认项目习惯与授权

- 用户明确要求新建或实现包时，继续完成必要代码、注册、测试和文档，无需为普通可逆编辑重复确认。仅讨论方案、问答或审查时不写源码；技能触发本身不扩大授权。
- 确认仓库根目录、`go.mod` 和工作区改动，读取根及目标目录生效的 `AGENTS.md`。用户最新要求优先，不覆盖已有改动。
- 在 CW 仓库读取 `docs/architecture.md`，按任务需要读取 `docs/testing.md`、`docs/development.md`。涉及并发、取消、外部命令、持久化一致性或清理前读取 `docs/defensive-patterns.md`。
- 选一到两个职责相近的现有包，沿路由、业务服务、存储/适配、配置和测试阅读实际实现。参考它们的命名、构造和响应方式，但不要复制违反当前规则的历史写法。
- 下文项目文件路径均相对于当前仓库根目录；本技能目录只用于读取随附参考。仓库规则是事实来源，不把 CW 的实现假设强加到其他项目。

## 先画清边界，再写代码

用简短说明列出：

1. **职责与资源**：新包拥有什么业务对象、状态和生命周期；哪些职责仍归已有包。
2. **调用与依赖**：谁调用新包，新包依赖哪些端口，具体实现在哪里创建。
3. **输入与状态**：公开参数、强类型内部值、持久化事实、可派生状态和秘密分别放在哪里。
4. **扩展需求**：用户已明确需要变化的协议、提供方、平台或存储；每类变化应落在哪个实现。
5. **验收证据**：哪些行为必须测试，哪些平台/资源尚未授权或当前环境无法验证。

说明可直接放在回复或任务要求的文档中。非平凡决策按项目规则写 Agent Note，不为了走流程另建大量 PLAN 或重复维护同一规范。只有无法从现有代码和用户意图确定、会改变公开行为的选择才询问用户；继续推进不依赖答案的工作。

## 分层与依赖方向

按实际职责选用以下位置；不要求每个包都具有全部层。

| 位置 | 拥有的职责 | 保持的边界 |
| --- | --- | --- |
| `pkg/<领域>` | 业务类型、不变量、用例编排、消费者需要的端口 | 不拼系统命令、不导入入口或具体适配层 |
| `routes/` | 请求绑定、认证/授权接入、调用用例、响应与流式适配 | 不维护领域状态，不直接查库或执行系统操作 |
| `storage/` | 查询、写入、事务、持久化编解码 | 不返回 HTTP 响应，不混入平台连接规则 |
| `infra/`、client、runner、probe | 系统命令、网络 SDK、硬件和平台行为 | 返回明确结果；释放自己创建的资源 |
| `cmd/server` | 创建具体实现、加载配置、依赖注入、启动与停止 | 不吸收领域业务逻辑 |

依赖方向以“具体适配实现依赖领域契约，领域服务使用注入的端口”为基准。接口放在使用者一侧，并仅包含该用例真正需要的方法，避免为了注入一个对象复制整套 SDK 接口。纯计算或稳定的具体实现无需为了形式另建接口；不要为只有一个调用点的短函数机械增加层次。

公开 DTO、领域对象和持久化对象按不同的所有权分开。业务状态不能由请求处理器、缓存、后台循环各维护一份；确定唯一事实来源和提交点。某层的修改不应迫使无关层理解其内部字段。

## 实现真实扩展点

- 为用户已经明确的变化设计契约，固定不变的流程留在公共服务。新增实现应主要增加自身代码及装配注册，不在公共路径反复增加“若是第一种协议”的分支。
- 可插拔或跨包扩展时，配置、驱动、提供方接口应能由独立包实现。若选择封闭类型集合，说明原因与新增变体的位置，不把封闭集合宣称为任意插件机制。
- 扩展贯穿请求解析、修改、公开详情、持久化往返、凭据、资源约束、实际执行、后台处理与退出清理。仅让结构体保存 `any` 或增加一个 Driver 接口，不算打通扩展。
- 解析 HTTP、JSON、配置文件和进程输入时完成校验，再把强类型值交给领域服务。无类型载荷只留在边界；不要在已校验的通用路径再次断言第一种实现的具体类型。
- 默认通过构造参数显式传入注册表或工厂，使服务和持久化共享同一份定义。沿用进程级注册确有必要时，记录它的装配顺序、并发与不可变要求；领域模型不能无说明地依赖隐式初始化。
- 资源唯一性、凭据共享范围和恢复能力由相应实现声明或提供策略，不用协议名称、目录种类或时间长度代替能力判断。
- 配置可读但运行实现未加载时，允许安全查看状态，实际动作返回明确的不支持错误；不得 panic、先写入操作意图再失败，或丢弃原配置。
- 平台差异放在项目约定的平台文件或适配实现中。公共领域模型不通过 `runtime.GOOS` 选择系统行为；不支持的平台返回明确结果。
- 不虚构适配边界。例如公共文件接口要求原生文件系统根时，普通 FTP/HTTP 客户端并不能直接代入；先明确用系统挂载适配还是抽象文件访问，再陈述支持范围。

涉及多实现、秘密、持久化或生命周期时，按需读 [扩展与异常检查](references/extension-checks.md)。不要把其中某个协议案例当作所有领域的强制设计。

## 沿用项目接入方式

- 用简单、见名知意的 Go 名称，导出契约说明失败条件、所有权和边界；注释与文档按当前项目语言编写。CW 使用中文。
- 路由注册、Operation/Registrar、字段命名和统一响应以当前相邻包及架构规范为准。权限定义、默认角色授权和实际资源归属检查需要一并接通；拥有管理权限不自动意味着可访问其他用户数据。
- 可由后端确定的内部字段不要求前端重复传入。可选业务选择使用清楚的默认值；并发预条件等保护字段说明来源及语义，不能只因“有默认值”删除真实能力。
- 领域配置拥有默认值，入口配置汇总；路径、端口、超时和并发限制不散落在业务函数中。生成资源改源后生成，不手改产物或 `go.sum`。
- 初始化、后台循环和关闭由明确所有者管理，使用项目现有 context、错误、事务及缓存惯例。长任务是否采用任务管理按真实业务和用户要求决定，不因网络调用存在就自动引入 Task。
- 凭据与普通配置分开，公开输出使用明确字段集合；复用项目安全设施并确认其长度、认证和用途边界，不把短密码方案默认套到长令牌/证书，也不为普通新包重写通用加密库。

## 验证职责和扩展，而不只验证首个实现

- 测核心用例、重要不变量及错误路径，并按实际变化覆盖跨层提交、清理和权限。用真实存储或文件验证状态；仅替换昂贵或不可确定的外部边界。
- 有明确第二种实现需求时，在现有测试文件加入最小但不同的测试实现：不同配置、公开输出、凭据或资源策略，走创建、修改、列表/详情和持久化完整链路；检查是否仍碰到第一种实现假设。它不是尚未实现协议的生产占位。
- 审查失败、取消、缺席实现及退出路径；正常路径通过不能证明后台或关闭流程安全。所有实际受影响包显式列出，未执行或 skip 的平台/集成检查仍是未验证。
- 优先追加到已有测试文件。从零创建的包尚无测试文件时，建立覆盖该包核心行为所需的最少测试文件；不要为一两个零散断言继续拆文件。
- 只运行当前仓库可核验的命令。CW 禁止 `go test ./...`，只测新包及显式相关包；改入口注册或配置时按规则做主服务构建并输出到 `/tmp`。硬件、外部服务、破坏性或跨平台验证不自行扩大授权。

## 完成前检查与交付

逐项确认依赖无循环、路由无业务实现、公共流程无首个实现类型假设、编解码与脱敏一致、平台策略留在边界、注册点及默认值齐全、资源有所有者、扩展支持范围与实际证据一致。

按项目要求完成格式、补丁检查、文档相对链接及 Agent Note 格式。CW 的新包非平凡变更在同一变更包含决策记录；只创建本技能本身不意味着修改项目源码或另建示例包。

报告实际交付的包职责、依赖与扩展方式，已运行的具体检查，以及未验证的平台/集成和仍需修改公共契约的边界。不要把“首个实现测试通过”描述为“任意后续实现无需改动”。

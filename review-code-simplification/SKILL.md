# 未提交代码精简审查

找出当前改动中值得合并的实现和可以减少的声明，给出行为保持不变、收益明确的最小建议。这里的“合并”指代码逻辑合并或复用，不是 Git 分支合并。使用中文报告。

## 范围与边界

- 默认只读。用户仅要求审查时，不修改源码、测试或配置，不暂存、提交、还原文件，也不自动生成报告文件。用户同时明确要求实施时，审查后按已授权范围执行，无需重复确认。
- 默认审查相对 `HEAD` 的最终工作区状态，覆盖暂存、未暂存和未跟踪源码。用户指定目录或文件时，以指定范围为准。
- 从改动中的声明和逻辑出发，按需阅读原有实现、调用方、测试和接口。原有代码可作为复用目标；发现项必须与本次改动有关，不扩展成全仓重构。
- 遵守当前仓库及目录的 `AGENTS.md`。兼容策略、包边界和命名按项目约定判断，不自行添加兼容层。

## 获取完整改动

先确认仓库根目录和规则，再查看变更清单。以下命令在仓库根目录执行；限定范围时，在 `--` 后传入实际路径：

```sh
git rev-parse --show-toplevel
git status --short --untracked-files=all
git diff --no-ext-diff --no-textconv --name-status --find-renames HEAD --
git diff --no-ext-diff --no-textconv --find-renames HEAD --
git ls-files --others --exclude-standard
```

`git diff HEAD` 不包含未跟踪文件，必须根据清单单独读取未跟踪源码。暂存与未暂存差异只在需要理解变更来源时分别查看，结论始终针对最终文件内容，避免漏掉已暂存代码或将两个版本重复计数。仓库尚无 `HEAD` 时，以索引和未跟踪清单定位候选，读取工作区现有内容。

先按清单区分源码、测试、文档、生成物和二进制；不把产物当作源码审查，相关生成物回查生成器。大量改动按包分批读取；不能把截断的 diff 当作已完整审查。报告实际覆盖范围和未读部分。结束前重新核对相关文件，若期间发生变化，重读受影响内容并更新引用。

## 两个审查方向

### 值得合并的代码

- 新增或修改的逻辑与同包已有实现重复，能够直接调用已有函数或方法。
- 多个分支、函数或方法执行同一操作序列，仅少量输入不同，能在清楚表达差异的前提下共享实现。
- 重复的参数转换、结果装配、校验或清理步骤，承担相同职责并有相同的错误处理和资源所有权。
- 相邻的辅助函数只是拆开同一个短小操作，合并后能减少无意义的跳转和传参。

判断合并价值时，比较职责、输入输出、副作用、错误路径和变化原因。优先已有实现、同函数内合并和同包复用。若需要引入模式开关、大量参数、回调、泛型框架或跨层依赖才能统一，先核算它们带来的复杂度；表面相似但职责或生命周期不同的代码不建议强行合并。

### 可以减少的声明

- 没有有效使用方的声明，包括重构后遗留的函数、方法、类型、字段、常量和变量。
- 只转发参数或返回值、没有实际语义或边界职责的包装函数、单字段包装类型和中间对象。
- 没有提供实际替换边界的接口、工厂、别名或选项结构；检查真实调用和测试使用后再建议收敛。
- 可由现有数据得到、却被重复保存和同步的字段或状态；检查缓存、快照、一致性和计算成本后再判断。
- 始终传入同一值且没有独立职责的参数，以及只用于一次简单表达式、移除后仍清晰的局部变量。
- 同义的常量、类型或数据结构，可复用现有声明且不会抹去不同的业务含义。

调用一次、实现只有一个、字段很少或代码行数短，都不足以单独证明声明多余。保留能清楚命名业务概念、缩短复杂表达式、提供实际测试替换点或承载所有权的声明。减少声明不是将多行压成一行，也不是把类型信息藏进无名结构、位置参数或动态容器。

## 核实每条建议

1. 阅读候选的完整实现、相关调用方和已有测试；使用 `rg` 搜索符号及同义逻辑，先当前包，再按调用关系扩展。优先使用可用的语言符号查询或结构化工具确认引用。
2. 不能仅凭文本引用数量认定未使用。按实际技术栈检查接口的隐式实现、反射或序列化、注册与回调、生成器、构建标签和平台文件。导出声明是否可删按项目的消费者和兼容约定判断；证据不足就标明不确定性。
3. 对合并或内联，核对求值次数与顺序、错误传播、日志、锁范围、`defer`、context 取消、资源释放、可变对象别名，以及零值或空值语义。只检查候选实际涉及的边界，不附带泛化审计。
4. 给出最小改法，明确复用哪个实现、移除哪些声明、哪些调用方需要随之调整。计算净收益时同时计入新 helper、参数、分支和依赖；无法可靠计数时用定性描述，不虚构减少行数。
5. 优先报告证据充分且减少维护成本的建议。不能确认行为等价或净收益的候选不列为确定可改项；仅在会影响决定时列出待核实原因。不要为了凑数量报告纯风格偏好。

只读审查通常以静态证据为主。有具体疑点且现有测试能提供有效证据时，只运行涉及包内的现有测试；不得默认全量测试，也不为审查新增或修改测试。报告实际执行的检查，并区分当前代码测试通过与建议实施后的行为已验证。硬件、外部服务和破坏性检查遵守项目的授权约束。

## 输出

先给值得采纳的建议，按收益、证据充分程度和实施成本排序。合并同一根因下的建议，避免既统计一组重复代码，又单列其每个声明重复计算收益。普通精简建议不冒充功能缺陷；若顺带发现确定的行为缺陷，单独标明并优先报告。

每条建议包含：

- **结论与位置**：标注“合并代码”或“减少声明”，用当前文件的可点击路径和准确行号定位；合并项同时给出重复处或复用目标的位置。
- **依据与改法**：说明具体冗余、现有调用关系，以及建议保留和移除的实现。必要时提供短小的前后示意，不输出未请求的大段补丁。
- **收益与约束**：说明能减少哪些声明、重复维护点或调用层次，以及已核实的行为边界和仍需验证的条件。

最后简述审查范围、实际检查和未验证部分。没有高价值建议时，明确写“未发现值得合并的代码或可明确减少的声明”，必要时解释少量看似可删但有保留理由的候选。不要将这项专项审查表述为完整的正确性或安全性审查。

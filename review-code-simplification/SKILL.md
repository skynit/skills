# 代码精简审查与重构

找出代码中有证据的重复、多余声明和理解障碍，提出或实施保持行为不变的最小改法。目标是降低阅读和维护成本，代码行数或文件数仅作为具体收益的一部分。这里的“合并”包括代码逻辑复用和文件归并，不是 Git 分支合并。使用中文报告。

## 范围与边界

- **审查模式**：用户要求分析、检查、审查或只点名技能时，默认只读，不修改源码、测试或配置，不暂存、提交、还原文件，也不自动生成报告文件。
- **实施模式**：用户明确要求精简、修改或重构代码，或已授权实施审查建议时，完成必要核实后直接执行授权范围内的改动，无需重复确认。技能自动选中不扩大授权，也不自动授权提交、发布或修改无关代码。
- 默认针对相对 `HEAD` 的最终工作区状态，覆盖暂存、未暂存和未跟踪源码。用户指定已有文件、目录或模块时，以指定范围为准，相关代码即使没有未提交改动也要读取。
- 从目标代码的声明和逻辑出发，按需阅读原有实现、调用方、测试和接口，确认现有写法承担的职责和存在理由；必要时查阅历史。原有代码可作为复用目标；候选须与本次目标有关，不扩展成全仓重构。
- 遵守当前仓库及目录的 `AGENTS.md`。兼容策略、包边界和命名按项目约定判断，不自行添加兼容层。

## 按任务选择审查方向

默认执行“值得合并的代码”“可以减少的声明”和“控制流与可读性”。只有用户明确要求对应方向，或本次目标中的职责分散、文件迁移或测试拆分已形成具体候选时，才继续读取并执行“routes 包整文件外移”“关联源码文件合并”“测试文件数量与合并”。对未触发的专项不逐包计数或展开全仓整理；用户明确要求的方向仍需报告有无可行建议。

## 获取完整改动

先确认仓库根目录和规则，再查看变更清单。以下命令在仓库根目录执行；限定范围时，在 `--` 后传入实际路径：

```sh
git rev-parse --show-toplevel
git status --short --untracked-files=all
git diff --no-ext-diff --no-textconv --name-status --find-renames HEAD --
git diff --no-ext-diff --no-textconv --find-renames HEAD --
git ls-files --others --exclude-standard
```

`git diff HEAD` 不包含未跟踪文件，必须根据清单单独读取未跟踪源码。暂存与未暂存差异只在需要理解变更来源时分别查看，结论始终针对最终文件内容，避免漏掉已暂存代码或将两个版本重复计数。仓库尚无 `HEAD` 时，以索引和未跟踪清单定位候选，读取工作区现有内容。

用户指定已有文件或模块时，另行读取该目标的完整实现，不能以 diff 为空认定没有需要检查的代码。

先按清单区分源码、测试、文档、生成物和二进制；不把产物当作源码审查，相关生成物回查生成器。大量改动按包分批读取；不能把截断的 diff 当作已完整审查。报告实际覆盖范围和未读部分。结束前重新核对相关文件，若期间发生变化，重读受影响内容并更新引用。

## 审查方向

### 值得合并的代码

- 目标逻辑与同包已有实现重复，能够直接调用已有函数或方法。
- 多个分支、函数或方法执行同一操作序列，仅少量输入不同，能在清楚表达差异的前提下共享实现。
- 重复的参数转换、结果装配、校验或清理步骤，承担相同职责并有相同的错误处理和资源所有权。
- 相邻的辅助函数只是拆开同一个短小操作，合并后能减少无意义的跳转和传参。

判断合并价值时，比较职责、输入输出、副作用、错误路径和变化原因。优先已有实现、同函数内合并和同包复用。若需要引入模式开关、大量参数、回调、泛型框架或跨层依赖才能统一，先核算它们带来的复杂度；表面相似但职责或生命周期不同的代码不建议强行合并。

### 可以减少的声明

- 没有有效使用方的声明，包括重构后遗留的函数、方法、类型、字段、常量和变量。
- 只转发参数或返回值、没有实际语义或边界职责的包装函数、单字段包装类型和中间对象。
- 没有提供实际替换边界的接口、工厂、别名或选项结构；检查真实调用和测试使用后再建议收敛。
- 可由现有数据得到、却被重复保存和同步的字段或状态；检查缓存、快照、一致性和计算成本后再判断。
- 始终传入同一值且没有独立职责的参数，以及只用于一次简单表达式、移除后仍清晰的局部变量。
- 同义的常量、类型或数据结构，可复用现有声明且不会抹去不同的业务含义。

调用一次、实现只有一个、字段很少或代码行数短，都不足以单独证明声明多余。保留能清楚命名业务概念、缩短复杂表达式、提供实际测试替换点或承载所有权的声明。减少声明不是将多行压成一行，也不是把类型信息藏进无名结构、位置参数或动态容器。

### 控制流与可读性

- 条件嵌套、长表达式或多段间接调用使行为难以追踪时，考虑提前返回、具名中间值、局部 helper 或合适的分支表达。按实际理解成本判断，不以行数或嵌套层数自动决定拆分；抽取和内联都要核实是否改善调用处的阅读顺序。
- 名称与实际内容、作用或副作用不符时，采用项目已有术语和简单、直接的名称。普通局部变量或惯用缩写不因短而改名；不能把个人风格偏好当作精简收益。
- 布尔参数、选项对象或复杂调用序列只有在实际增加理解成本时才调整，优先现有类型和入口；避免为消除一个参数引入更多类型或层次。
- 保留代码难以直接表达的业务意图、约束和取舍注释。确认注释过时或仅机械复述表达式后再建议删除或改写。
- 表面更短的写法仍需核对实际语义，例如条件成立与空值回退、同步抛错与异步拒绝、返回类型、迭代顺序和分配成本。性能敏感路径先确认代价，不凭语法形式认定等价或更快。

### routes 包整文件外移

- 检查本次涉及的 `routes` 包中，哪些文件可以整体迁到上一层或其他已有目录。“外移”明确指整份文件迁出 `routes`，不能用抽取几个业务函数代替这项结论。
- 阅读候选文件的全部职责、导入和调用方，判断目标目录的包职责是否匹配；参数解码、中间件、HTTP 响应转换和路由绑定通常仍属于接口适配层。
- 核实包名调整、自身包引用、循环依赖、未导出声明的跨文件引用、同名声明冲突，以及构建标签、平台文件和相对路径资源。测试文件是否需要随迁也要说明。
- 分别报告“可整体迁移”“需调整后才能整体迁移”“不建议整体迁移”，给出原文件、目标目录和必要改动。不能把需要拆分文件或重设包边界的方案表述为直接迁移。
- 优先已有目录；仅为搬离 `routes` 新建包、增加导出声明或转发层时，核算新增复杂度。整文件迁移一般不减少文件总数，单独说明职责归属的收益。

### 关联源码文件合并

- 检查同一包内是否把一个功能分散到多个文件，重点关注只有少量声明的辅助文件，以及需要频繁互相跳转的关联实现。
- 以共同职责、调用关系和变化原因判断合并价值，不能仅凭文件短、调用一次或总文件数多就认定应合并。不同协议、授权、审计或生命周期的独立职责不强行拼接。
- 明确每组保留文件和并入文件，优先沿用已有文件。文件归并与重复逻辑合并分别说明，不能把单纯搬动声明计算为减少声明或代码行数。
- 核实 imports 及别名、全部声明和注释、包初始化顺序、构建条件、嵌入或相对路径资源、生成指令和文档引用。按原职责保持方法、错误处理、锁、取消和资源释放行为；不顺带改名或改接口。
- 给出合并前后的实际文件数量，避免把文件减少量等同于 Git 变更文件减少量。区分实际存在的文件与暂存后又删除的记录；合并原有文件可能增加修改或删除记录。

### 测试文件数量与合并

- 逐包统计本次涉及包内的全部测试文件，检查能否收敛到一到两个；用户或项目明确要求此数量时按要求审查，否则作为归并目标，不当作通用硬性限制。
- 对照 `HEAD` 区分已有分布和本次新增的拆分。历史包已超过目标数量时说明现状，不因当前审查自动扩展成全仓测试整理。
- 优先把相同或关联功能的测试并入已有测试文件，特别检查仅为一两个测试新增文件的情况。共用的 fixture、辅助函数和常量随对应测试归并，不为合并新增辅助测试文件。
- 保留测试包声明和构建条件的边界。例如 Go 的 `package tcp` 与 `package tcp_test` 应分别归并；不同平台、构建标签、集成测试运行条件不能在合并时被抹去。
- 核实测试、子测试、断言、辅助声明、清理逻辑和执行条件完整保留，检查重复名称、import 别名、共享状态及初始化顺序。不能通过删减测试来达成数量目标，也不能声称文件合并提高了测试覆盖率。
- 按包列出当前数量、建议数量、保留文件、并入文件和不能合并的理由。仅审查时不修改测试；明确授权实施后，只运行受影响包内测试，不运行全量测试。

## 核实每条建议

1. 阅读候选的完整实现、相关调用方和已有测试；使用 `rg` 搜索符号及同义逻辑，先当前包，再按调用关系扩展。优先使用可用的语言符号查询或结构化工具确认引用。
2. 不能仅凭文本引用数量认定未使用。按实际技术栈检查接口的隐式实现、反射或序列化、注册与回调、生成器、构建标签和平台文件。导出声明是否可删按项目的消费者和兼容约定判断；证据不足就标明不确定性。
3. 对合并或内联，核对求值次数与顺序、错误传播、日志、锁范围、`defer`、context 取消、资源释放、可变对象别名，以及零值或空值语义。只检查候选实际涉及的边界，不附带泛化审计。
4. 给出最小改法，明确复用哪个实现、移除哪些声明、哪些调用方需要随之调整。计算净收益时同时计入新 helper、参数、分支和依赖；无法可靠计数时用定性描述，不虚构减少行数。
5. 优先报告证据充分且减少维护成本的建议。不能确认行为等价或净收益的候选不列为确定可改项；仅在会影响决定时列出待核实原因。不要为了凑数量报告纯风格偏好。

只读审查通常以静态证据为主。有具体疑点且现有测试能提供有效证据时，只运行涉及包内的现有测试；不得默认全量测试，也不为审查新增或修改测试。报告实际执行的检查，并区分当前代码测试通过与建议实施后的行为已验证。硬件、外部服务和破坏性检查遵守项目的授权约束。

## 实施与验证：仅在已授权实施时执行

1. 从已核实的候选中选择收益明确、行为等价的最小改法。授权范围和目标已清楚时直接实施；仍影响公开契约或需要新的产品决策时，先说明具体取舍并澄清未决部分。
2. 按一个可独立验证的行为边界推进改动，保留用户已有修改及暂存状态。沿用现有命名、函数、类型和扩展点；只有解决已证实的问题时才增加抽象。改动清晰到可以单独审阅，不为精简顺带修复功能缺陷。
3. 保持输入输出、副作用及顺序、错误、权限、日志、并发和资源所有权等相关契约。文件迁移或归并还须保留构建条件、声明可见性及资源路径。精简失败时只修正或撤销本次操作，保留用户原有工作。
4. 按适用 `AGENTS.md` 选择受影响包内最小必要的测试、编译或静态检查，确认实际命中用例。相关小步可在同一验证边界集中检查；不得默认运行全量或递归测试、无关包检查，也不逐个文本编辑重复执行测试。纯文档任务只做文件级检查。
5. 保留现有测试的行为断言和覆盖；确需因文件迁移或内部结构变化调整测试组织时，说明原因并保留相同验证能力。必要的新用例优先加入已有相关测试文件，不靠删除、跳过或弱化断言让改动通过。
6. 交付前查看最终差异，确认没有无关变更，源码和测试的文件归并完整，临时产物已清理。报告实际验证结果及无法验证的条件；现有失败与本次引入的失败分别说明，不把未执行或零用例执行算作通过。

## 输出

审查模式先给值得采纳的建议，按收益、证据充分程度和实施成本排序。合并同一根因下的建议，避免既统计一组重复代码，又单列其每个声明重复计算收益。普通精简建议不冒充功能缺陷；若顺带发现确定的行为缺陷，单独标明并优先报告。

每条建议包含：

- **结论与位置**：标注“合并代码”“减少声明”“改善可读性”“整文件外移”“源码文件合并”或“测试文件合并”，用当前文件的可点击路径和准确行号定位；合并项同时给出重复处或复用目标的位置，文件迁移项给出目标目录。
- **依据与改法**：说明具体冗余、现有调用关系，以及建议保留、移除或迁移的实现和文件。必要时提供短小的前后示意，不输出未请求的大段补丁。
- **收益与约束**：说明能减少哪些声明、重复维护点、调用层次或实际文件，以及已核实的行为和包边界、仍需验证的条件。文件数量较多时用表格列出各组或各包的前后数量。

实施模式先说明已经完成的改动、为什么更易理解或维护，以及行为保持的依据；给出关键文件位置、实际验证和未覆盖部分，待讨论建议与已完成改动分开陈述。

最后简述实际覆盖范围、检查和未验证部分。对用户明确要求的审查方向，即使没有建议也要说明结论；例如没有适合整体迁出的文件，或相关包的测试文件数量已符合目标。没有高价值建议时，说明未发现值得采纳的精简或文件整理项，必要时解释少量看似可删但有保留理由的候选。不要将这项专项审查表述为完整的正确性或安全性审查。
